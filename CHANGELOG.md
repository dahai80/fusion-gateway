# Changelog

All notable changes to Fusion-Gateway are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
Each release entry mirrors the GitHub Release generated by `.github/workflows/release.yml`
on tag push; this file is the maintained, human-curated counterpart.

## [Unreleased]

### Fixed (shell RBAC user roles, 2026-10-27) — #359

- **`PATCH /api/v1/shell/users/{id}` persisted role names that do not exist in
  the role store** — roles landed verbatim on the account, so a client bug could
  plant a phantom role that never appears in `GET /shell/roles` and is
  unmanageable in the admin UI (the symmetric delete-side guard `role in use`
  already existed). Both user-write paths now validate every role against
  `RoleStore.Exists` (built-in or custom) and reject unknown names with
  **400 `role_rejected`** listing them — mirroring the menu-permissions PUT
  gate in `internal/shell/roles.go`. POST validates its assigned default role
  set through the same helper so the default can never drift out of the
  resolvable set.

### Fixed (admin dashboard render, 2026-10-27) — #360

- **Insights Latency page unmounted entirely by a recharts invariant** — the
  anomaly overlay drew `ReferenceLine` elements without `yAxisId`, so recharts
  defaulted to axis id `0` which does not exist on charts whose Y axes are
  named `left`/`right`, threw
  `Invariant failed: Could not find yAxis by id "0"`, and React unmounted the
  whole page whenever at least one detected anomaly fell inside the selected
  window. Both charts (TTFT + TPOT) now set `yAxisId="left"` on their
  `ReferenceLine` marks. Regression-pinned by
  `tests/e2e/tests/08-latency-render.spec.js` (no invariant, both cards, ≥6
  percentile curves, overlay non-fatal).

### Fixed (admin replay contract, 2026-10-27)

- **`POST /admin/api/insights/logs/{id}/replay` answered 404 for a log row
  without a captured payload** — `GET /v1/models` poll rows and retention-pruned
  payload partitions have a log row but no `fg_request_payloads` entry;
  `insights.Payload` returns `pgx.ErrNoRows` and the handler leaked it as a
  404, violating the documented "no captured request body" contract. The
  handler now maps `ErrNoRows` to **409** (same as an empty captured body)
  and reserves 500 for real fetch failures. The e2e replay test also mints
  its own 4-token chat request (master key from config) instead of replaying
  an arbitrary stored row — a stored row can carry a 64k-token context the
  local engine needs minutes to regenerate, blowing the test timeout.
- **`03-channels.spec.js` full-suite flake** — the delete-confirm step checked
  `Popconfirm` visibility immediately after the delete click, racing the
  popover render and silently skipping the confirm. It now waits for the
  popover (3s) before deciding.

### Fixed (admin dashboard data, 2026-10-27) — #354

- **`/v1/messages` bridge path still logged Prompt=0** — follow-up to #351:
  the `captureEventUsage` fix only covered the native MessagesProvider loop,
  but local-MLX serving via an openai-compatible backend (localSlotProvider
  shadow role, #210) resolves to nil in `resolveMessagesProvider`, so
  production local traffic takes the OpenAI-conversion else branch. There the
  token budget was seeded `InputTokens: 0` (discarding the tokenizer count)
  and the SSE bridge's exact `include_usage` counts were never exposed. The
  bridge-path budget now carries the tokenizer estimate, the stream path
  stamps exact upstream usage after `bridge.Finalize()` via the new
  `anthropicSSEBridge.UsageTotals()`, and the non-stream path reuses
  `stampCachedUsage` over the captured completion body.

### Fixed (admin dashboard data, 2026-10-27) — #351

- **Logs page 0/0/0 tokens on streaming `/v1/messages`** — the hardened
  stream forward loop (keepalive enabled, the production path) never called
  `captureUsage`, so every streaming Claude Code request logged zero
  prompt/completion/total tokens. Both forward loops now share
  `captureEventUsage`, which also reads `message_start`'s nested
  `message.usage` — the only wire shape carrying `input_tokens`, so the
  Prompt column was 0 even through the backward-compat loop.
- **Logs page flooded by blank poll rows** — `GET /v1/models` and
  `POST /api/v1/shell/manifests` are polled several times per second across
  keys and filled the 10k request-log ring until the most-recent rows were
  almost all blank model/channel noise. `withMiddleware` now skips request
  logging (memory ring + persist sink) for those endpoints; the handlers
  still run.
- **Insights Latency chart y-axis blown up by non-stream rows** — non-stream
  requests stamp `ttft_ms` as the full response duration (by design), and the
  Latency percentile aggregation did not split by stream mode, so a
  multi-minute non-stream generation stretched the TTFT percentiles past
  200,000 ms. TTFT percentiles now filter to streaming rows
  (`FILTER (WHERE is_stream)`); requests/errors/avg_duration keep counting
  all generation rows, and the source stamp semantics stay untouched for the
  other `ttft_ms` consumers (detectors, rules, reports, search).

### Added (config file protection, 2026-10-27) — #349

- **Config guard: last-good backup + self-healing load/reload** — closes the
  2026-10-27 production outage class where an external textual edit
  duplicated a YAML block in `config.yaml` and the gateway fatal-looped on
  start. `config.BackupFile` snapshots `config.yaml` → `config.yaml.lastgood`
  before every overwrite (admin writes) and after every successful load.
  `LoadWithRecovery` / `ReloadWithRecovery` (startup, fsnotify, and
  `/admin/config/reload`) quarantine the broken file as
  `config.yaml.corrupt-<ts>` and restore from the last-good copy, logging the
  recovery loudly — the gateway comes up instead of crash-looping.
- **Config-fatal exit code 78 (`EX_CONFIG`)** — when recovery is impossible
  (no backup or the backup is broken too), the process exits 78 instead of
  the generic 1, and the new `--check-config` flag validates a config file
  with the same contract. `start.sh` preflights the config before launch so
  fusion-supervisor sees a fast, distinct config failure rather than a
  start/die crash loop (upstream ask: fusion-supervisor#47).

### Added (manifest schema v2 grouping, 2026-10-24) — #297

- **Shell manifests gain optional `group` / `group_title` / `group_title_en` /
  `sort` fields** — display-only aggregation for the shell host's two-level
  menu (e.g. five fusion-office apps collapse into one `Fusion Office`
  top-level entry). `group` is a stable id shared by siblings
  (`^[a-z0-9-]{1,64}$`, empty = ungrouped, fully backward compatible);
  titles cap at 128 chars; `sort` orders siblings within a group (stable,
  ties by id). Siblings must agree on the group title — first registered
  wins, mismatch logs a throttled WARN, never a rejection. No group-level
  RBAC: module visibility stays per-module. Validated at registration and
  heartbeat refresh; `Registry.List()` passes the fields through verbatim
  (only `api_key` is zeroed). Static `web_shell.manifests` entries get the
  same mapstructure keys.

### Added (fusion-security union-web module wiring, 2026-10-24) — #296

- **`web_shell.modules.fusion-security` static proxy wiring** — upstream
  `http://127.0.0.1:11454`, credential is a tenant-assigned fusion-security
  API key (the upstream validates its own keys; a gateway `fm-`/`fg-` key
  would be rejected), plus a static fallback manifest so the menu entry
  survives upstream restarts. The health poller probes through the proxy
  with the injected credential and keeps the entry `online`. Documented the
  self-keyed-module pattern (leave self-registration env off until the
  module's registration body carries the same `api_key`, or #294's
  dynamic-credential preference would inject the wrong key). Upstream gaps
  (frontend static serving, registration api_key) tracked in
  fusion-security#40.

### Fixed (Anthropic system array flattening, 2026-10-24) — #293

- **Anthropic→OpenAI auto-convert no longer JSON-marshals the system array
  into the prompt.** Claude Code always sends `system` as an array of content
  blocks; the convert path's `default` arm marshaled it wholesale, so the
  block wrappers (`{"type":"text","text":"..."}`), escaped newlines, and the
  per-request `x-anthropic-billing-header` block (random `cch=` value) landed
  in the model prompt as literal JSON — polluting the input and defeating
  fusion-mlx's native-route `_BILLING_HEADER_PREFIX` prefix-cache
  stabilization. New `systemToString` mirrors the message flattening: keep
  `type=="text"` blocks, join with blank lines, drop blocks starting with
  `x-anthropic-billing-header:`. All-billing input yields no system message
  at all.

### Fixed (shell proxy stale static api_key, 2026-10-24) — #294

- **Dynamic registration's credential now wins on the shell proxy when it
  points at the same upstream as the static entry.** Incident shape: a module
  that self-registers gets an fm- key issued/rotated by the gateway (the
  module validates incoming traffic against it), while the static
  `web_shell.modules[].api_key` in config.yaml went stale — the proxy kept
  injecting the old key and the module returned 401 API_KEY_INVALID
  (18/min, console unusable) until an operator hand-edited config.yaml.
  Resolution order now: dynamic credential (module-supplied api_key or the
  fm- key `EnsureServiceKey`/`RotateServiceKey` keep on the registry entry)
  when upstreams match; static api_key otherwise (fallback for never-
  self-registered modules, and the correct credential for the #256
  engine-vs-bridge split where upstreams differ). Divergence (both set,
  same upstream, different keys) logs a throttled WARN (1 per 5m per module,
  #281-style). Acceptance: rotation → zero manual config edits; static-only
  modules unchanged; K1 issuance semantics unchanged (plaintext exactly
  once, key_id stable).

### Fixed (heartbeat-carried manifest refresh, 2026-10-23) — #284

- **Heartbeat body now converges stale shell manifest ext fields.** Modules
  re-register the full manifest on startup then only heartbeat, so ext-field
  drift (fusion-cowork grew 7→11 pages; the shell sidebar kept showing 7)
  never converged while the module stayed alive, and the persisted store
  kept replaying the stale manifest across gateway restarts. The heartbeat
  body is OPTIONAL with a documented semantic: empty (or id-less) body =
  historical liveness-only ping, not persisted; a body carrying the module's
  current manifest atomically refreshes the stored entry (same validation
  gates as registration), persists it, and keeps the issued `fm-` service
  key intact (#261/#277 — key_id stable, no plaintext re-reveal, upstream
  credential retained). A refresh that fails validation returns 400
  `manifest_refresh_rejected` but still counts for liveness — a mis-shaped
  manifest greys nothing and fails loudly instead of silently.

### Fixed (log-flood + stale-key observability hardening, 2026-10-23) — #281/#282/#283

- **Shell heartbeat-denial WARN flood throttled (#281).** A module sending a
  permanently wrong credential logged one `shell heartbeat denied` WARN every
  15s forever (1944/day in the current log), burying real errors. Denial
  WARNs are now throttled to 1 per 5m per `(id, reason)` via the new
  `internal/logthrottle` helper, while the new counter
  `fusion_gateway_shell_heartbeat_denied_total{module_id,reason}` counts
  every denial so a misconfigured module stays observable in `/metrics`.
  Wire behavior (status codes, envelopes) unchanged.
- **Invalid-key 401 surfaces the key hash prefix (#282).** A client stuck on
  a rotated/stale key was only identifiable by grepping gateway logs. The
  401 body now carries `key_hash_prefix` (8 hex chars of SHA-256 —
  identifies the key family, never the key) so client-side tooling can
  self-diagnose, the `invalid api key` WARN gains the same attribute, and
  `fusion_gateway_auth_invalid_key_total{hash_prefix}` makes a recurring
  stale key spottable in `/metrics`. Missing-key 401 unchanged.
- **OTel export-failure log flood throttled (#283).** With
  `otel_enabled: true` and no OTLP collector on `localhost:4317`, the SDK
  logged one `traces export: exporter export timeout` error per batch (~1
  per 30s, 194/day). `InitTracing` now installs a throttled
  `otel.ErrorHandler`: first occurrence of each distinct error logs
  immediately, then at most 1 per 5m, while
  `fusion_gateway_otel_errors_total` counts every occurrence. Tracing
  itself unchanged — exports keep retrying and recover once a collector
  appears.

### Added (shell E6 admin surfaces, 2026-10-23) — #275

- **Session-gated E6 admin surfaces: adapters vault / connectors / config
  overrides / audit / roles + menu matrix** (fusion-web-shell#42, migration
  E6). Five `/api/v1/shell/*` surfaces follow the #271 keys precedent:
  - **Adapters vault** — `GET/PUT /api/v1/shell/adapters[/{platform}]` +
    `POST .../test`: per-platform credentials stored AES-256-GCM encrypted at
    rest (key derived domain-separated from `auth.master_key`); only the
    masked projection (`credentials_masked`, last 4 chars) ever leaves the
    gateway; an empty credentials map on PUT keeps existing secrets
    (rate-limit-only edits cannot wipe them).
  - **Connectors** — `GET/PUT /api/v1/shell/connectors[/{id}]` +
    `POST .../test`: config-first connector documents persisted with
    server-side validation problems surfaced inline; `credential_ref`
    resolves from the vault, secrets never inline. Package
    validation/enable still delegates to fusion-plugins-ecosystem#30.
  - **Config overrides** — `GET/PUT /api/v1/shell/config/{key}`: open key
    vocabulary (`{defaults, overrides}` projection); PUT is effective
    immediately (modules merge over template defaults at runtime).
  - **Audit** — `GET /api/v1/shell/audit?user=&action_class=` (admin or
    auditor role): hash-chain audit trail (`read|write|approval|agent_run|
    config|auth` classes, `ok|denied|error` outcomes); a tampered row or any
    row after a chain break surfaces `integrity_ok: false`. Login
    success/failure and every E6 mutation record rows.
  - **Roles + menu matrix** — `GET/POST /api/v1/shell/roles`,
    `DELETE /api/v1/shell/roles/{name}`,
    `GET/PUT /api/v1/shell/menu-permissions`: built-in roles (admin/user/
    auditor) fixed with derived write classes; custom roles grant write
    classes from the audit vocabulary (≤64, built-in collision 409); a role
    still assigned to users is rejected with the reason; menu defaults
    derive from the live manifest registry, overrides replace them and
    reference only resolvable roles.
  - Stores persist under `store.data_dir` (`shell_adapters.json`,
    `shell_connectors.json`, `shell_config_overrides.json`,
    `shell_audit.json`, `shell_roles.json`, `shell_menu_permissions.json`);
    a corrupt store degrades that surface, never wedges the shell.

### Fixed (shell stale manifest expiry, 2026-10-23) — #276

- **Stale dynamic registrations whose upstream refuses connections are now
  expired.** The shell health poller sweeps heartbeat-expired dynamic
  registrations after each probe pass: when the upstream actively refuses
  connections the registration is dropped (and the persisted store updated),
  so fresh shell sessions stop receiving the dead endpoint within one
  heartbeat interval. Entries whose upstream still accepts connections stay
  listed as unreachable (greyed); builtins are protected. A restarted
  service re-registers via its own start.sh — no operator action needed.

### Added (shell home projects passthrough, 2026-10-22) — #273

- **`home.projects` poll sources in module manifests (shell #41).** The
  manifest `home` block gains an optional `projects` list
  (`id`/`label`/`label_en`/`endpoint`) so a Home Projects/Spaces section can
  aggregate per-module workspaces. Entries validate with the same
  gateway-absolute endpoint rules and 32-entry cap as the other ext fields,
  pass through camelCase on the wire, and persist in the registry
  round-trip. Omitting the list leaves existing manifests byte-identical.

### Added (shell session-gated keys proxy, 2026-10-22) — #271

- **Session-gated `/api/v1/shell/keys` proxy for the Settings page.** The
  master key can never reach a browser, so the K2 `withMasterKey` gate left
  the shell Settings → API Keys page with no callable surface. Adds four
  admin-role session routes (`list`/`create`/`rotate`/`revoke`) under
  `/api/v1/shell/keys` that reuse the K2 user-key handlers unchanged — the
  control plane stays master-gated at `/api/v1/keys`, the shell gets its own
  session-gated path. Non-admin sessions receive `403 permission_error`;
  rotate/revoke responses are stripped of the non-secret key rows exactly as
  the master surface does.

### Added (user API keys, 2026-10-22) — #262

- **Gateway-issued `fk-` user API keys with scope enforcement on `/v1/*`.**
  Master-gated CRUD at `/api/v1/keys`: create (`{name, scopes, tenant?, ...}`,
  plaintext returned exactly once, SHA-256-only storage, tail-4 display),
  rotate (dual-active grace via `auth.key_rotation_grace`, default 24h —
  `key_prev_hash` + `key_rotated_at` keep the old key valid inside the
  window), revoke (soft — status `revoked`, row retained for audit, auth
  rejects immediately). New `middleware.ScopeEnforce` maps `/v1/*` inference
  paths to modules (chat/rag/design/agent) and returns
  `403 permission_error` when a scoped key lacks the module grant —
  `["chat", "rag:embed", "cowork:runs:create", "*"]` matrix; empty scopes
  (legacy keys) pass unchanged. Optional `tenant` binds the key to a team so
  the request path derives `X-Fusion-Tenant` from the credential. Every
  authenticated `/v1/*` request now propagates the caller identity
  downstream as `X-Fusion-Principal` (set by the auth middleware, never a
  client passthrough).

### Added (gateway-issued module service keys, 2026-10-22) — #261

- **`fm-` service keys reverse the module credential direction.** A
  `POST /api/v1/shell/manifests` body that omits `api_key` now gets an
  `fm-<module-id>-<32hex>` key generated by the gateway — the plaintext is
  returned exactly once (`raw_key` + non-secret `key_id`), the module
  configures its own auth to accept it, and the proxy injects it as the
  upstream Bearer credential. SHA-256 hashes (current + pre-rotation) live
  on the registry entry, never on the manifest — the list API and
  registration responses stay key-free; the plaintext rides the existing
  `manifest.APIKey` channel (existing proxy path, `List()` zeroing, #230
  persistence). A body that carries `api_key` keeps the historical
  module-supplied path; idempotent re-registration retains the issued key
  without re-revealing the plaintext.
- **Heartbeat re-auth with the issued key.**
  `POST /api/v1/shell/manifests/{id}/heartbeat` accepts the module's `fm-`
  key (SHA-256 hash compare against the registry entry bound to the path
  id), in addition to `web_shell.admin_key` / master key for back-compat.
  The route moves off the standard fg-key chain — an `fm-` Bearer would be
  401'd by `APIKeyAuthWithStore` before the gate could evaluate it.
- **Rotation with dual-active grace.**
  `POST /api/v1/shell/manifests/{id}/key/rotate` (admin-plane) issues a
  replacement key; the previous key stays heartbeat-valid for
  `web_shell.key_rotation_grace` (default 24h) or until the first heartbeat
  carries the new key, whichever comes first. Builtin/static manifests are
  rejected 409 like deletion.
- **Revocation with structured degradation.**
  `DELETE /api/v1/shell/manifests/{id}/key` (admin-plane) clears all key
  material; heartbeats 403, the proxy serves 503 `module_key_revoked`
  (A5 envelope, never an unauthenticated forward), and the shell host greys
  the module via the existing unreachable mechanism.
- Service-key state (ids, hashes, rotation time, revoked flag) persists in
  `shell_manifests.json` and survives restarts.

### Added (cloud-model allowlist, 2026-10-22) — #265

- **`routing.cloud_models` allowlist pins everything else to local
  fusion-mlx.** When non-empty, only models matching a listed pattern may
  route to a cloud backend; local-set models, unknown model names, and the
  empty model (default-model backfill) are forced local at P0.15 — no
  overload/token/ratio heuristic can hand a local-only name to a cloud
  endpoint. Patterns follow the auth `allowed_models` convention (exact,
  `*`, trailing-`*` prefix, case-insensitive). Empty list (default) keeps
  the historical hybrid behavior, so existing deployments are unaffected.
  The same guard applies to the rerank decision path. Exposed on
  `GET/PUT /admin/api/config/routing` as `cloud_models`. Note
  `fallback.model_mapping` is applied after routing, so the list must carry
  client-facing aliases (`claude-*`), not the mapped model id.

### Changed (glm-5 default cloud backend, 2026-10-21)

- **`glm-5` is now the gateway's cloud default.** New `backends.glm-5`
  entry (`type: anthropic`, `base_url: https://glm.tathr.com`, `timeout:
  300s`) matches the channel `~/test/startGlm5-3.sh` points Claude Code at.
  `routing.fallback.cloud_default` was `fusion-mlx-openai` — a backend name
  that never existed in `backends`, so every cloud-routed request 503'd.
- **`routing.mode: local` → `hybrid`.** `mode: local` is a fast-path that
  bypasses P6, so a request for `glm-5` was forced onto fusion-mlx and got
  `400 Model 'glm-5' not found`. Under `hybrid`, `glm-5` (absent from the
  local model set) falls through to P6 `model_not_available_locally` →
  cloud → `glm-5`. Local-exclusive models still hit P0.2 and stay local.
- **`routing.fallback.model_mapping` values `glm5.2` → `glm-5`.** No backend
  served `glm5.2`; Claude Code's `claude-*` aliases mapped to a model name
  the sole cloud backend rejects.
- **`cloud_routing.strategy`: `weighted` → `weight`, weights `{glm-5: 100}`.**
  `weighted` is not a case in `CloudStrategy.Select` (the switch matches
  `weight`), so it fell to `default: return backends[0]` — and `backends`
  comes from a map iteration, making the cloud pick a coin flip between
  `kimi-k2.7-code` and `glm-5`.
- **`routing.ratio_tiers.enabled: true` → `false`.** Its three rules target
  `volcengine`/`dashscope`/`qianfan`, all `enabled: false`, so any request
  with output/input ratio ≤ 0.6 got `CloudTarget` = a provider that does not
  exist → `resolveCloudProvider` 503. Unreachable under `mode: local`; a
  guaranteed failure under `hybrid`. P4.5b's single `output_input_ratio_threshold`
  still diverts high-ratio requests.

Verified live against the running binary: `glm-5` → `channel=glm-5`
(non-stream, SSE, and `/v1/messages` Anthropic wire), `claude-sonnet-4-6` →
mapped to `glm-5`, `mlx-community/Qwen3.5-4B-MLX-4bit` → `backend=local`.

Known upstream quirks of the glm-5 endpoint (not gateway defects, confirmed
by calling it directly): `message_start.usage.input_tokens` is 0,
`message_delta.stop_reason` is empty on the streaming wire, and stream ids
are `msg_<uuid>` rather than `chatcmpl-*`.

### Fixed (shell ext-path routing, 2026-10-21) — #256

- **Manifest-declared ext endpoints route to the self-registered upstream,
  not the static-pinned one.** Acceptance verify of fusion-mlx#1281/#1285
  hit a conflict: `web_shell.modules.fusion-mlx.upstream` pinned the engine
  (:11434) while the self-registered manifest declared the web bridge
  (:11471) — the bridge-only ext endpoints (`/api/search/models`,
  `/api/notifications`) 404'd through the gateway, breaking ⌘K search and
  the notification bell for mlx.
- New per-path override in the /shell/ proxy (#256, issue option 2 — keeps
  #232 static-wins semantics for everything else): when the request path
  matches an endpoint the manifest declares in `searchProviders`/
  `notifications` (exact or segment-boundary prefix), the proxy dials the
  dynamic registration's own upstream and injects that upstream's

### Fixed
- **Local-exclusive models cloud-diverted on a full-GPU host** (#148 follow-up).

  BUSY" signal where local-exclusive has no cloud alternative anyway. Extracted
  `localExclusiveDecision` helper; two new tests pin both branches
  (`TestDecide_LocalExclusiveModel_GPUMemoryLowStaysLocal`,
  `TestDecide_LocalExclusiveModel_BreakerOpenStillCloud`). Verified live:

## [0.9.8] - 2026-09-01

### Fixed
- **`auto_start` no longer fights fusion-supervisor over the fusion-mlx
  lifecycle** (#141). fusion-supervisor (`fusion-sv`, a Rust daemon) manages
  fusion-mlx as one of its supervised services — starting it in the core layer
  on `fusion-sv up` and stopping it authoritatively on `fusion-sv down`. The
  gateway's own `server.auto_start` independently launched fusion-mlx on
  startup and stopped it on shutdown, so on a supervisor-managed host the two
  were uncoordinated: the gateway could stop a healthy mlx mid-request (or
  double-start it, racing the supervisor's probe-first recovery).
  - Fix: `supervisorActive()` detects the supervisor explicitly — `FUSION_SV_ACTIVE=1`
    env var OR the supervisor UDS socket (`/tmp/fusion-sv.sock`) present — and
    `autoStartLocal` then skips the launch, returning `started=false`.
    `autoStopLocal` takes the `started` flag and is a no-op when the gateway
    did not start the backend, AND skips when the supervisor is active (the
    supervisor owns the stop). The handoff is no longer left to the
    supervisor's probe-first heuristic; detection is explicit.
  - `auto_start` remains the standalone fallback for non-supervisor
    environments (bare gateway, single-binary, CI); on managed hosts the
    supervisor is authoritative. `config.AutoStartConfig` struct +
    `config.example.yaml` document the handoff.
  - Tests: `TestSupervisorActive_EnvGate`, `TestSupervisorActive_SocketProbe`
    (hermetic — swaps the socket path to `t.TempDir`, never touches the real
    `/tmp/fusion-sv.sock`), `TestSupervisorActive_NeitherActive`,
    `TestAutoStartLocal_SkipsWhenSupervisorActive` (sentinel command never
    runs), `TestAutoStopLocal_OnlyStarted` (no-op when not started). 35 cmd
    tests race-green; 2863 tests across 26 packages green.

## [0.9.6] - 2026-08-30

### Fixed
- **`withAdminOnly` routes returned 403 for a valid admin-login JWT** (#137/#138).
  `withAdminOnly` checked `middleware.IsAdmin` BEFORE the `withMiddleware` auth
  chain ran, and the admin module issues its own JWT (`AdminClaims{Role:"admin"}`
  via `/admin/api/login`) that the chain never parsed into `middleware.Principal`.
  The two auth systems were unbridged, so a valid admin Bearer reached **403** on

    `AuthMethod=="admin-jwt"` so the chain neither overwrites the bridged role
    nor 401-rejects an admin-JWT Bearer. Fail-closed: invalid/non-admin token
    leaves `Principal` untouched and `IsAdmin` denies (403); a no-op when the
    admin module is disabled. Master-key reject still fires first (plane
    separation preserved).
